# План: перенос частей KomaruGram на Rust

## Сначала цифры

В `Telegram/SourceFiles` около 1,42 млн строк C++. Из них собственного кода
KomaruGram и AyuGram (`ayu/`) около 72 тыс. строк, то есть 5%. Остальное —
Telegram Desktop, который мы каждый релиз подтягиваем из апстрима
(последний раз 7.3.4: 634 файла и 65 тыс. добавленных строк за одну
версию).

Отсюда главное правило плана: **код апстрима на Rust не переписываем.**
Если переписать, например, `history/` (183 тыс. строк) или `mtproto/`
(22 тыс.), каждое обновление Telegram превратится из «наложить патч и
разобрать 13 конфликтов» в ручной перенос всех изменений апстрима на свой
Rust-код. После двух-трёх версий клиент отстанет от Telegram навсегда.

«Половина клиента» в буквальном смысле (около 700 тыс. строк) поэтому не
цель. Цель другая: **весь код, который принадлежит KomaruGram и не
приходит из апстрима, постепенно переносится на Rust**, если от этого
есть польза: надёжность, скорость или меньше кода. Интерфейс на Qt
остаётся на C++, потому что он завязан на lib_ui и сигналы Qt.

## Что даст Rust и чего не даст

Даст:
- безопасную работу с памятью там, где мы разбираем чужие данные: файлы
  плагинов, gist со значками, сетевые ответы, базу удалённых сообщений;
- быстрые регулярные выражения для фильтров (crate `regex` без
  катастрофического отката);
- изолированные модули с тестами на `cargo test`, которые не требуют
  собирать весь клиент.

Не даст:
- быстрого запуска. Замер 3 ноября: окно без аккаунта появляется через
  1,6 с, первая строка лога через 0,2 с. Долгий запуск с аккаунтом нужно
  сначала замерить, и он почти наверняка в загрузке данных Telegram, а не
  в нашем коде;
- ускорения сборки. Наоборот, к трём часам CI добавится компиляция Rust.

## Состояние

- 3 ноября: этап 3 (хранилище) сделан первым, потому что это самая тяжёлая
  для сборки часть нашего кода. `sqlite_orm.h` (25 тыс. строк шаблонов)
  удалён, `ayu_database.cpp` стал обёрткой над crate `komaru_core`. Схема
  таблиц та же, что делал sqlite_orm, так что старые сборки открывают ту же
  базу. Порядок дальше: от тяжёлого к лёгкому.

## Как подключить Rust к сборке

1. **Corrosion** (CMake-модуль) собирает crate и линкует его как
   статическую библиотеку в `Telegram`. Подключается в
   `Telegram/CMakeLists.txt` одной функцией `corrosion_import_crate`.
2. Граница C++/Rust — простой C API (`include/komaru_core.h`), без cxx:
   никакой генерации кода при сборке. Через границу идут только числа и
   байты; строки отдаются в обратных вызовах и копируются на стороне C++.
   Паники ловятся на каждой функции.
3. Код лежит в `Telegram/rust/`. Внешних crate нет: SQLite берётся из
   `sqlite3.c`, который клиент и так собирает, поэтому cargo собирает всё
   за секунды и без сети. Тесты: `cargo test` со системной SQLite.
4. CI:
   - Windows x64 и x86: `rustup target add x86_64-pc-windows-msvc
     i686-pc-windows-msvc`, кэш `~/.cargo` и `target/`;
   - Linux: rustup в Dockerfile образа сборки. Образ после этого
     пересоберётся один раз и дальше берётся из GHCR.
5. Профиль `release` с `lto = "thin"`, `panic = "abort"`, чтобы не
   раздувать бинарник (он и так 285 МБ).

## Этапы

Каждый этап заканчивается рабочей сборкой и тем, что старый C++-код
удалён, а не лежит рядом.

### Этап 0. Каркас (1–2 дня)
- `Telegram/rust/` с crate `komaru_core`, Corrosion и cxx в CMake.
- Одна функция для проверки цепочки, например версия crate в «О
  программе».
- CI собирает все три платформы.
- Готово, когда: сборка зелёная, бинарник вырос не больше чем на 2 МБ.

### Этап 1. Значки и статусы KomaruGram (2–3 дня)
- `ayu/features/komaru/komaru_badges.*`: загрузка и разбор `badges.txt`,
  `donates.txt`, `statuses.txt` из gist.
- На Rust: разбор строк, цветов, ссылок на паки и id эмодзи. Сеть и
  отрисовка остаются в C++.
- Тесты на все форматы строк из gist, включая битые.
- Готово, когда: значки и статусы показываются как раньше, тесты
  проходят в CI.

### Этап 2. Фильтры сообщений (3–5 дней)
- `ayu/features/filters/`: компиляция и применение регулярных выражений
  к тексту сообщений.
- На Rust: движок фильтров на crate `regex`, кэш скомпилированных
  выражений.
- Плюс: не бывает зависаний на «плохих» выражениях, которые в
  `QRegularExpression` откатываются экспоненциально.
- Готово, когда: те же фильтры дают те же совпадения на наборе тестовых
  сообщений, а скорость не хуже.

### Этап 3. Хранилище удалённых и изменённых сообщений (1–2 недели)
- `ayu/data/` (`ayu_database`, `messages_storage`) на sqlite_orm.
- На Rust: `rusqlite` с той же схемой и миграциями, запись в фоне.
- Самый рискованный этап, потому что затрагивает данные пользователя.
  Нужны: миграция без потерь, проверка на копии реальной базы, откат на
  старую версию без порчи файла.
- Готово, когда: старая база читается новой версией, а «Посмотреть
  удалёнки» показывает то же, что до переноса.

### Этап 4. Мост плагинов (1 неделя)
- Сейчас запросы плагинов проходят через `komaru_plugins.cpp`: JSON по
  stdin/stdout, base64, сериализованные запросы MTProto.
- На Rust: протокол хоста, проверка и разбор сообщений от хоста, очередь
  запросов. Отправка в MTProto остаётся в C++, потому что идёт через
  соединение клиента.
- Плюс: строгий разбор входа от процесса, которым управляет чужой код
  плагинов.
- Python-хост остаётся Python, так как плагины exteraGram написаны на
  Python.

### Этап 5. По мере надобности
- Переводчик (`ayu/features/translator`): HTTP-клиенты и разбор ответов.
- Message shot и прочее, где больше логики, чем интерфейса.
- Интерфейс настроек и меню не переносим: это Qt и lib_ui.

Итого на Rust окажутся примерно 20–30 тыс. строк из 72 тыс. собственного
кода. Остальное — интерфейс и правки внутри файлов апстрима, им лучше
оставаться в C++.

## Риски

| Риск | Что делаем |
| --- | --- |
| Время CI растёт | Кэш cargo, `sccache` для Rust, сборка crate один раз на платформу |
| Размер бинарника | `lto = "thin"`, `opt-level = "z"` для некритичных crate, следим за ростом на каждом этапе |
| Windows x86 | Проверять `i686-pc-windows-msvc` с первого этапа, не в конце |
| Паника в Rust роняет клиент | `panic = "abort"` плюс `catch_unwind` на каждой границе cxx и возврат ошибки в C++ |
| Конфликты с апстримом | В файлах апстрима меняем только вызовы, вся логика в своих файлах |
| Данные пользователя (этап 3) | Резервная копия базы перед миграцией, переключатель на старое хранилище на одну версию |

## С чего начать

Этап 0 и этап 1: каркас и значки. Риска для данных нет, результат виден
сразу, и на нём проверяется вся цепочка: CMake, cxx, CI на трёх
платформах. Решение о следующих этапах принимаем после того, как увидим,
сколько это добавило ко времени сборки и размеру бинарника.
